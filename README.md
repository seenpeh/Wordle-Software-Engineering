# وردل فارسی

پیاده‌سازی بازی وردل به زبان فارسی به‌صورت **static frontend** با HTML، CSS و
JavaScript خالص — بدون هیچ فریم‌ورک، وابستگی زمان اجرا یا مرحله‌ی build.

این مخزن گزارش آزمایش درس مهندسی نرم‌افزار است و تمرکز آن، علاوه بر خود
نرم‌افزار، بر **فرآیند کار تیمی با git** است.

🔗 **آدرس سایت:** https://seenpeh.github.io/Wordle-Software-Engineering/

## معماری نرم‌افزار

نرم‌افزار از چند ماژول ES مستقل تشکیل شده که **از طریق رویداد** با هم صحبت
می‌کنند، نه با فراخوانی مستقیم. این تصمیم باعث شد دو عضو تیم بتوانند هم‌زمان و
بدون وابستگی به کد یکدیگر پیش بروند.

```
┌──────────────┐   wordle:input          ┌──────────────┐
│  keyboard.js │ ──────────────────────▶ │   game.js    │
│   input.js   │                         │  (کنترلر)    │
└──────────────┘                         └──────┬───────┘
       ▲                                        │
       │       wordle:guess-evaluated           │
       └────────────────────────────────────────┤
                                                │
┌──────────────┐   wordle:game-ended            │
│   stats.js   │ ◀──────────────────────────────┘
│stats-modal.js│
└──────────────┘
```

### قراردادهای رویدادی

| رویداد | منتشرکننده | شنونده | داده |
|---|---|---|---|
| `wordle:input` | `input.js` | `game.js` | `{action, value}` |
| `wordle:guess-evaluated` | `game.js` | `keyboard.js` | `{evaluations}` |
| `wordle:game-ended` | `game.js` | `stats.js` | `{won, targetWord}` |
| `wordle:stats-updated` | `stats.js` | `stats-modal.js` | `{stats}` |

### ماژول‌ها

| فایل | نقش |
|---|---|
| `js/config.js` | ثابت‌های بازی: طول کلمه، تعداد حدس، وضعیت حروف |
| `js/board.js` | ساخت گرید ۶×۵ و به‌روزرسانی خانه‌ها |
| `js/state.js` | بافر حدس در حال تایپ، مکان‌نمای ردیف، وضعیت بازی |
| `js/words.js` | دیکشنری ۲۸ کلمه‌ی پنج‌حرفی فارسی |
| `js/evaluate.js` | مقایسه‌ی حدس با کلمه‌ی هدف |
| `js/game.js` | کنترلر: اتصال ورودی به وضعیت، رنگ‌آمیزی، پایان بازی |
| `js/input.js` | نرمال‌سازی ورودی (شامل تبدیل «ي»/«ك» عربی به فارسی) |
| `js/keyboard.js` | کیبورد مجازی، کیبورد فیزیکی، بازخورد رنگی کلیدها |
| `js/stats.js` | ذخیره‌سازی آمار در `localStorage` |
| `js/stats-modal.js` | نمایش آمار در `<dialog>` با اعداد فارسی |

## اجرای محلی

```bash
npm start        # سرو کردن روی http://localhost:3000
npm test         # اجرای آزمون‌ها با node --test
```

پروژه هیچ وابستگی زمان اجرا ندارد؛ `npm start` فقط یک سرور static موقت
بالا می‌آورد. آزمون‌ها با test runner داخلی Node اجرا می‌شوند.

## ساختار شاخه‌ها

```
main                              شاخه‌ی محافظت‌شده و پایدار — منبع استقرار
 └── dev                          شاخه‌ی یکپارچه‌سازی — همه‌ی شاخه‌ها اینجا ادغام می‌شوند
      ├── feature/ui-keyboard             کیبورد مجازی و ورودی
      ├── feature/game-core               هسته‌ی بازی
      ├── feature/stats-storage           آمار، مودال و چیدمان موبایل
      ├── feature/font-rubik              تغییر فونت به Rubik
      ├── feature/font-estedad            تغییر فونت به Estedad
      ├── feature/checkguess-refactor     بازآرایی منطق بررسی حدس
      ├── feature/pages-deploy            پیکربندی استقرار مستمر
      └── feature/readme                  مستندسازی پروژه
```

### چرا این ساختار

سه نوع شاخه با اهداف متفاوت به کار رفته است:

- **`main`** — همیشه قابل استقرار. هیچ‌کس مستقیماً روی آن کامیت نمی‌کند و فقط
  از طریق درخواست ادغام به‌روز می‌شود. هر push روی این شاخه یک استقرار
  خودکار روی GitHub Pages راه می‌اندازد.
- **`dev`** — محل یکپارچه‌سازی. کار دو عضو تیم اینجا کنار هم می‌نشیند و تعارض‌ها
  اینجا حل می‌شوند، پیش از آن‌که چیزی به `main` برسد.
- **`feature/*`** — هر شاخه یک قابلیت مشخص و مستقل. نام‌گذاری با پیشوند
  `feature/` و یک توصیف کوتاه از همان قابلیت.

## گزارش تعارض‌ها

در طول پروژه **سه تعارض** رخ داد و همگی حل شدند. در هیچ‌کدام از آن‌ها کار یکی
از دو عضو تیم دور ریخته نشد؛ در همه‌ی موارد هر دو طرف تلفیق شدند.

### تعارض ۱ — ادغام `dev` در `feature/game-core`

**کامیت حل:** `cd0b85d`

هر دو عضو تیم مستقلاً فایل‌های پایه‌ی یکسانی ساخته بودند، بنابراین git هیچ جد
مشترکی برای مقایسه نداشت و سه تعارض هم‌زمان رخ داد:

```
CONFLICT (add/add):  css/styles.css
CONFLICT (content):  index.html
CONFLICT (add/add):  js/app.js
```

| فایل | تصمیم |
|---|---|
| `index.html` | اسکلت معنایی `dev` (با `aria-label`) مبنا قرار گرفت و گرید بازی جای placeholder نشست؛ تگ `<script>` تکراری حذف شد |
| `js/app.js` | هر دو راه‌اندازی ترکیب شدند — چون معماری رویدادمحور است، ماژول‌ها بدون وابستگی مستقیم کنار هم نشستند |
| `css/styles.css` | هر دو استایل‌شیت نگه داشته شد و رنگ‌های هارد‌کد‌شده‌ی کیبورد به custom propertyهای مشترک تبدیل شدند |

### تعارض ۲ — تعارض عمدی روی فونت (بین دو درخواست ادغام)

**کامیت حل:** `e5cc891`

این تعارض **به‌صورت برنامه‌ریزی‌شده** ایجاد شد تا سناریوی واقعی تغییر هم‌زمان
یک خط توسط دو نفر تمرین شود:

1. شاخه‌ی `feature/font-estedad` فونت اصلی را `Estedad` کرد و با
   [PR #3](https://github.com/seenpeh/Wordle-Software-Engineering/pull/3)
   وارد `dev` شد.
2. شاخه‌ی `feature/font-rubik` که همان خط `--font-family` را به `Rubik` تغییر
   داده بود، در
   [PR #4](https://github.com/seenpeh/Wordle-Software-Engineering/pull/4)
   با تعارض مواجه شد.

**تصمیم:** به‌جای انتخاب یک‌طرفه، هر دو `@font-face` نگه داشته شدند و ترتیب
فونت‌ها به این شکل حل شد:

```css
--font-family: "Estedad", "Rubik", Tahoma, Arial, sans-serif;
```

`Estedad` فونت اصلی ماند چون یک فونت variable فارسی است و برای متن فارسی رابط
بازی خوانایی بهتری دارد؛ `Rubik` به‌عنوان fallback دوم برای متون لاتین حفظ شد.

### تعارض ۳ — ادغام مجدد `dev` در `feature/game-core`

**کامیت حل:** `ed257d5`

پس از حل تعارض فونت روی `dev`، شاخه‌ی `feature/game-core` دوباره ادغام شد و

شدند و توکن‌های رنگ و اندازه‌ی گرید هم دست‌نخورده ماندند.

> **یک اشکال که هنگام حل این تعارض کشف شد:** آدرس CDN فونت Estedad روی `dev`
> خطای `404` می‌داد، چون jsDelivr برچسب `@latest` را برای مخازن `gh`
> پشتیبانی نمی‌کند (فقط برای بسته‌های npm). در نتیجه فونت بی‌صدا به fallback
> برمی‌گشت. آدرس به نسخه‌ی پین‌شده‌ی `@8.5` اصلاح شد و بارگذاری صحیح هر دو
> فونت در مرورگر تأیید شد.

## محافظت از شاخه‌ی main

روی شاخه‌ی `main` قانون محافظت (branch protection rule) اعمال شده است:

- ✅ **Require a pull request before merging** — امکان push مستقیم روی `main`
  وجود ندارد
- ✅ **Require approvals** — هر درخواست ادغام باید توسط عضو دیگر تیم تأیید شود

در نتیجه تنها راه رسیدن تغییرات به `main` و انتشار روی سایت، عبور از یک
درخواست ادغام بازبینی‌شده است.

## استقرار مستمر

استقرار با **GitHub Actions** و به‌صورت خودکار انجام می‌شود.

فایل پیکربندی: [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)

### جریان کار

```
push روی main
      │
      ▼
┌─────────────┐        ┌──────────────────┐
│  job: test  │ ─────▶ │   job: deploy    │
│  npm test   │        │  GitHub Pages    │
└─────────────┘        └──────────────────┘
   اگر شکست بخورد            اجرا نمی‌شود
```

مرحله‌ی استقرار به مرحله‌ی آزمون وابسته است (`needs: test`)، بنابراین اگر
آزمون‌ها شکست بخورند هیچ نسخه‌ی معیوبی منتشر نمی‌شود.

چون پروژه static است و مرحله‌ی build ندارد، کل مخزن مستقیماً به‌عنوان artifact
آپلود می‌شود. همه‌ی مسیرهای پروژه نسبی هستند، بنابراین سرو شدن سایت در
زیرشاخه‌ی `/Wordle-Software-Engineering/` مشکلی ایجاد نمی‌کند.

### آزمون‌ها

مجموعه‌ی آزمون شامل **۲۴ آزمون** است که با `node --test` اجرا می‌شوند و
نرمال‌سازی ورودی، اولویت وضعیت کلیدها، اعتبار دیکشنری، ارزیابی حدس و
محاسبات آمار را پوشش می‌دهند.
